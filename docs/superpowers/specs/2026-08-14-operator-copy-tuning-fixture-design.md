# 操盘手纯文案调优与内置 IP 演练资料设计

## 目标

把 Skill Forge 从“146 个 Skill 全量调试项目”收缩成面向 IP 操盘手的纯文案质量调优工作台。操盘手不再导入资料，也不再接触治理、共享组件、视觉、生图、发布、监控或数据能力；项目默认使用一套明确标注为合成演练数据的“赵玥玥”IP 材料，按真实工作台链路逐个试跑文案 Skill。

## 已确认范围

### 默认调优队列

默认队列固定为 32 个 Skill：

- IP 建档、定位与策略：10 个。
- 用户洞察与选题规划：8 个。
- 文案生产与平台表达：14 个。

7 个与爆款拆解、评论回复、CTA、朋友圈和私域有关的文案 Skill 暂不进入默认队列；需要时由项目所有者另行启用。其余 107 个不进入操盘手调优流程。

### 不在范围内

- 所有视觉、生图、海报、配图和版式能力。
- 所有治理 Skill 和共享质量组件。
- 资料入库、标签、索引、召回、路由、权限、Schema 和状态流转。
- 发布、投流、监控、数据复盘和方法资产治理。
- 删除 146 个运输 Skill 包，或者改变 ClipMind 线上源文件。
- 自动调用线上模型、自动发布、自动写库或改变外部业务状态。

## 方案比较

### 方案 A：删除非文案 Skill

优点是目录最小；缺点是破坏完整运输清单、让后续工程回溯困难，也会造成大量无意义删除。否决。

### 方案 B：保留完整运输包，只收缩操盘手队列

保留 146 个 Skill 作为工程参考，`inventory/tuning-order.json` 只列 32 个默认文案 Skill；调试脚本拒绝启动不在队列中的 Skill。优点是改动小、可追溯、操盘手界面干净。采用此方案。

### 方案 C：另建一个精简仓库

隔离最强，但会产生双仓同步、基线漂移和维护重复。当前没有必要。否决。

## 内置“赵玥玥”演练 IP

### 数据性质

“赵玥玥”只是一套合成演练人物，不对应或影射任何真实个人。所有经历、产品、案例、数据和表达样本都必须在文件顶部标注为 `MOCK`，不得作为真实宣传、客户证明或外部事实使用。

### 资料组成

版本化资料放在 `fixtures/ip/赵玥玥/`：

- `README.md`：合成数据声明和使用边界。
- `MATERIALS.md`：材料目录、用途和可用性。
- `PROFILE.md`：已确认演练档案。
- `EVIDENCE-INDEX.md`：事实编号、来源位置和证据强度。
- `原始材料/01-人物访谈.md`：经历、转折、价值观和工作方式。
- `原始材料/02-业务与产品.md`：服务对象、产品阶梯、交付边界和禁用承诺。
- `原始材料/03-用户访谈与评论.md`：目标用户原话、显性痛点、深层动机和异议。
- `原始材料/04-案例记录.md`：完全虚构且带证据边界的项目案例。
- `原始材料/05-表达语料.md`：口头禅、句式、喜欢与禁用表达。
- `原始材料/06-历史内容样本.md`：不同质量层级的文案样本。
- `原始材料/07-内容表现数据.md`：合成内容表现、反馈和限制条件。
- `原始材料/08-阶段目标与选题池.md`：当前业务阶段、内容目标和待生产选题。
- `scenarios.json`：32 个 Skill 各自的固定任务和应读取材料。

### 初始化方式

`progress.py init` 在本地 IP 素材库为空时自动把内置演练资料复制到被 Git 忽略的 `IP素材库/`，并把档案标记为可直接试跑。已有用户材料或已有档案时绝不覆盖。进度状态记录：

- `profile_mode: builtin_fixture`
- `active_ip_fixture: zhao-yueyue`
- `ip_profile_status: ready`

## 操盘手调优流程

1. 操盘手发送“开始调试”或“开始调试下一个 Skill”。
2. Codex 初始化进度；素材库为空时自动启用赵玥玥演练资料。
3. 进度脚本只返回 32 个白名单 Skill 中当前唯一一项。
4. Codex 读取当前 Skill、其不可修改基线、对应 `scenarios.json` 任务和指定 IP 材料。
5. Codex 按当前 Skill 模拟工作台执行，生成一份完整内容结果，并保存固定输入和首轮输出。
6. 操盘手只评价生成结果，回复“OK”或“不OK + 修改建议”。
7. Codex 把反馈分为当前 IP 个案、可复用文案方法和产品契约变化：
   - 个案只用于本轮输入或演练档案，不进入通用 Skill。
   - 可复用方法只修改当前 Skill 已允许的判断、组织、示例和表达板块。
   - 身份、触发、上下游、输入输出、工具、权限、人工边界和关键结构变化一律阻断。
8. 修改后先通过机器边界检查，再使用完全相同的任务和材料重新生成。
9. 重复反馈与复跑，直到操盘手明确确认。
10. 最终再次校验，通过后生成含最终 `SKILL.md`、差异和验证证据的回收包；不自动上线。

## 不可修改结构加固

现有检查继续保留，并增加三层门禁：

1. **队列门禁**：以清单而非目录名前缀判断是否允许操盘手调优；不在 32 个默认队列中的 Skill 无法启动或打包。
2. **基线门禁**：为默认队列记录 `references/original.md` 的 SHA-256。基线发生任何变化时立即阻断，避免候选和基线被一起替换。
3. **契约门禁**：继续比较封装、标题序列、角色、适用场景、输入输出契约、变量、JSON 结构、人工边界和外部动作；混合型小红书图文 Skill 只能调整文字方法，视觉职责和结构保持冻结。

校验器、基线锁、调试清单和测试都属于工程文件，操盘手反馈不能授权 Codex 修改它们来“让检查通过”。

## 文件职责

- `inventory/tuning-order.json`：32 个默认文案 Skill 的唯一顺序。
- `inventory/optional-copy-skills.json`：7 个默认关闭的按需文案 Skill。
- `inventory/baseline-locks.json`：默认队列的原始基线哈希。
- `fixtures/ip/赵玥玥/`：版本化合成演练资料和固定场景。
- `scripts/progress.py`：初始化演练资料、维护唯一活动 Skill、限制默认队列。
- `scripts/skill_guard.py`：验证调优范围、基线完整性和候选契约。
- `scripts/finalize.py`：仅为队列内且校验通过的 Skill 生成回收包。
- `scripts/project_check.py`：同时检查 146 个运输包完整性和 32 个操盘手队列一致性。
- 操盘手说明文件：只描述内置演练资料和纯文案反馈流程。

## 错误与恢复

- 演练资料缺失或损坏：停止生成，报告缺失文件，不凭空补造。
- 当前 Skill 没有场景映射：项目检查失败，不能开始该 Skill。
- 发现已有私有材料：保留现有材料，不自动覆盖或混入演练资料。
- 修改触碰冻结层：校验失败，恢复候选 Skill 到上一个通过版本。
- 操盘手反馈要求产品能力变化：记录为工程建议，不修改 Skill。
- 同输入复跑没有改善：明确报告未改善，继续迭代，不得用换题制造改善。

## 验收标准

- 默认调试队列恰好 32 个，顺序与已确认白名单一致。
- 7 个按需文案 Skill 不会出现在默认 `next` 结果中。
- 视觉、治理、共享组件及其他排除项不能被 `start` 或 `finalize`。
- 空素材库初始化后可以直接使用赵玥玥演练资料；已有材料不会被覆盖。
- 32 个 Skill 都有固定场景和明确材料映射。
- 每份演练资料都明确标注 `MOCK`，没有真实联系方式、真实客户或可误认的外部事实。
- 修改允许的文案方法可以通过；修改原始基线、角色、变量、Schema、工具、人工边界或关键结构会失败。
- 首轮和每次复跑使用同一固定输入。
- 只有操盘手明确确认后才能生成最终回收包。
- 项目完整测试和分发一致性检查通过。

## 假设

- “赵玥玥”按用户要求作为合成演练 IP；不从互联网补充或猜测真实人物信息。
- 本次不修改 146 个运输 Skill 的线上来源或业务契约，只修改 Skill Forge 的调优范围、演练资料、工作流和本地门禁。
- 32 个默认 Skill 是当前正式范围；7 个按需 Skill 只保留清单，不默认启用。
